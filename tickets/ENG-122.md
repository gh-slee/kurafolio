# ENG-122: Decide how the full Linux unit suite fits its CI job budget

## Goal

The `python-312-linux` job runs the full synthetic suite in a single step with a
25-minute job limit. Measured runs are close enough to that limit that a normal
runner can be cancelled after the tests have finished but before the job records
success. Record the measurements and choose a durable budget or split so a
review does not depend on runner luck.

## Context

- PR #116, `python-312-linux`, 2026-11-25/26: the unit step finished `Ran 1525
  tests in 1482.098s` (24m42s) at 19:53:25 and the 25-minute job limit cancelled
  it at the same second. The run at the same code earlier took about 19 minutes.
- A temporary 40-minute limit let the same suite pass at 25m21s, then it was
  reverted because it is outside IMP-007F's scope.
- The job also runs language/publication checks and four report demos after the
  unit step, so a 25-minute limit cannot absorb runner variance.
- Slowest single tests in the measured run were about 70 s, 68 s and 67 s; the
  duration is spread across report, source and Web cases rather than one test.

## Requirements

- Record the measured unit-step duration and the limit used on at least three
  recent runs, with run links.
- Choose one durable option: a documented job limit with margin, splitting the
  suite into parallel jobs with a stable partition, or reducing the measured
  runtime.
- If the limit changes, state why the new value covers the measured worst case
  and the report/demo steps.
- Keep the same tests and failure visibility; do not skip or deselect cases to
  fit the budget.
- Update `.github/workflows/ci.yml` and the CI documentation together.

## Acceptance criteria

- [ ] AC-ENG-122-01: The ticket records at least three measured unit-step
      durations with run links and the job limit in force for each.
- [ ] AC-ENG-122-02: The chosen option is applied and a pull-request run at the
      new configuration completes without cancellation at the measured worst
      case.
- [ ] AC-ENG-122-03: No test is removed, skipped or deselected to fit the
      budget, and the pull-request checks still show the same test count.
- [ ] AC-ENG-122-04: CI documentation states the limit or partition and the
      measured evidence behind it.

## Plan

- Gather the recent `python-312-linux` step durations and limits from the run
  history.
- Compare a raised job limit with a stable parallel partition of the suite.
- Apply the chosen change and verify it in a pull-request run.
