# OPS-104: Publish ready-to-pull V2 images and a pull-only install (WEB-008)

## Goal

Installing Kurafolio today means cloning the repository and building an image. Someone who only wants to run it should need Docker and one compose file. Publish versioned V2 images for the two common processor types and a compose file that pulls them, with a tested install, upgrade and restore path.

## Context

### Background

- This is what turns the project from "the owner's instance" into something another household can run. It follows OPS-015 because only verified behaviour should be published.
- Publishing an image is a public release. It needs the owner's explicit approval each time; no agent publishes on its own (AGENTS.md).

### Scope

- In scope: a release workflow that builds amd64 and arm64 images from a tag, a pull-only compose file, provenance and a software bill of materials attached to the image, install, upgrade and restore instructions, a test that follows them on a clean machine.
- Out of scope: automatic updates, a Helm chart or other orchestrators, a hosted service, images of the shipped SQLite application, publishing itself until the owner approves.

### Implementation notes

- Start from the V2 compose file and hardening delivered by OPS-021 and the source-only build context from `scripts/docker_context.py`. The published image must be the one the pre-PR gate (`scripts/check_pr_image.py`) builds, not a second recipe.
- Tags: an exact version and a digest. The compose file pins the digest. No floating `latest` unless the owner asks for it.
- The workflow runs only on a version tag pushed by the owner and stops for approval before the push to the registry.
- Upgrade means: pull the new image, run the documented migration command, start. A test takes a volume created by the previous version through that path.
- State exactly which platforms were verified (OPS-015: Apple Silicon Mac with Docker Desktop; Linux amd64 in CI). Do not claim others.

### Where to start

- The V2 compose file and operator documentation from OPS-021; `compose.yaml` for the hardening pattern.
- `scripts/docker_context.py`, `scripts/check_pr_image.py`, `.github/workflows/ci.yml`, `scripts/dependency_inventory.py`.
- [web-release-acceptance.md](../docs/web-release-acceptance.md), [publishing.md](../docs/publishing.md), [SECURITY.md](../SECURITY.md).

## Acceptance criteria

- [ ] Given a machine with Docker and no checkout, when the operator follows the install page, then a V2 instance starts from pulled images, the setup page loads, and a synthetic import completes.
- [ ] Given an instance on the previous published version, when the operator follows the upgrade page, then data remains and the new version reports itself.
- [ ] Given a backup from the published image, then it restores into an empty second instance on the same image digest.
- [ ] Images exist for amd64 and arm64, carry provenance and a bill of materials, and their contents match the dependency inventory.
- [ ] The workflow cannot publish without a version tag and a manual approval; a dry run on a pull request builds but does not push.
- [ ] The documentation names the verified platforms and says that others are untested.
- [ ] No image, tag or release is published by this ticket's pull request. Publication is a separate step the owner performs or approves.

### Tests

- A CI job that builds both architectures and runs the smoke test on amd64.
- An opt-in Docker test for install, upgrade and restore from a local registry.

## Decisions needed

1. Registry and name. Recommendation: GitHub Container Registry under the repository owner, because it needs no extra account.
2. Whether a floating tag such as `latest` exists. Recommendation: no; pin versions so an upgrade is always deliberate.
3. Who triggers a release. Recommendation: only the owner, by pushing a version tag, with a manual approval step before the push.
