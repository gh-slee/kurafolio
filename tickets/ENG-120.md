# ENG-120: Cut the pull requests and CI runs that only move ticket paperwork

## Goal

Every ticket now costs the owner extra pull requests that change only ticket files: one to record a Gate A approval, and often one after the merge to mark the ticket `done`. Each one runs the full CI matrix and a Docker image build, although no code changed. Fold that paperwork into the pull requests that already exist and give ticket-only changes a light check path, without losing the approval evidence on `main` or the privacy and language guards on any change.

## Context

- At `94f0fd8`, 106 of the 260 commits on `main` change only files under `tickets/`. `tickets/` is about 1 MB of a 52 MB repository, so the cost is noise and CI time, not size.
- **Mark-done pull requests.** At least ten commits on `main` exist mainly to mark a ticket `done` after its build merged, most recently #76 (ENG-115), #67 (ENG-112), #63 and #61. [tickets/README.md](README.md#quick-start-for-an-agent) step 5 already says to set `status: done` and `pr:` in the pull request's final commit, but the same step sets `status: in_review` while review repairs are pending and never says to set `done` again. ENG-115's Log records exactly that: "status set to `done` in a follow-up PR because the merge left it at `in_review`". Nothing checks the rule.
- **Approval-only pull requests.** On 2026-11-17 the Gate A records for ENG-115, ENG-113 and ENG-114 merged as three separate pull requests (#69, #70, #71), each before its Build plan existed. [docs/spec-development.md](../docs/spec-development.md#the-ticket-is-the-spec) says approvals reach `main` through a merged pull request; it does not require a pull request of their own. The planning exception lets a planning session edit only Context, Build plan, Plan and Decisions needed, so a planner cannot record an approval today.
- **CI.** [.github/workflows/ci.yml](../.github/workflows/ci.yml) runs eight jobs (`python-312-linux`, `docker-foundation`, `browser-workflow`, `parser-sdk-packages`, `postgres-foundation`, `postgres-ingestion`, `postgres-identity`, `postgres-sources`) on every push and pull request, so a ticket-only pull request shows 16 checks. `python-312-linux` also runs `check_language.py`, both `check_publication.py` modes, the full unit suite and four report demos.
- **Image gate.** [AGENTS.md](../AGENTS.md#verified-commands) ("Before every PR (including documentation-only changes)") and [docs/development.md](../docs/development.md#pre-pr-candidate-image-gate) require `python scripts/check_pr_image.py`, a Docker build and smoke run, before every pull request.
- `main` has no branch protection or required checks today. A job skipped by a job-level `if:` reports as skipped, which GitHub treats as passing if required checks are added later; a workflow skipped by workflow-level `paths-ignore` reports nothing and would leave a required check pending.
- Ticket text is public, so the privacy guard must keep running on ticket-only changes. `tests/test_tickets.py` and `python3 scripts/tickets.py check` validate the board.
- ENG-116 (backlog) also holds `public-docs-agent-rules`; the two must not run at the same time.

## Requirements

Done in the build pull request:

- A builder sets `status: done`, `pr:` and the outcome Log line in the last commit it pushes before the owner's review, including the last commit of every review-repair round. `in_review` marks only a branch with repairs still outstanding.
- An automated check run by CI on pull requests fails when the pull request's own ticket (the ticket whose `branch:` names the pull request's head branch) is not `done` with `pr:` set, and passes otherwise. A pull request with no own ticket (planning, filing or approval-only) is not affected.
- `tickets.py` keeps working offline: it does not ask GitHub whether a pull request merged.
- The quick start, `docs/spec-development.md`, `.claude/agents/builder.md` and `.codex/agents/builder.toml` say this. A pull request closed without merging still sets the ticket back to `ready`, as today.

Gate A records with other work:

- A Gate A record (`gate_approval`, `spec_approved` and the Log line quoting the owner) goes in the pull request that files the ticket or carries its Build plan, not in a pull request of its own, unless the owner asks for a separate one.
- The planning exception also lets a planning session record a Gate A that the owner gave in that conversation, quoting the owner's words in the Log. Nothing else about who may record an approval changes.
- When the gated text changes before approval, the Build plan is checked against the approved text before the pull request is opened.

Light checks for ticket-only changes:

- A change is ticket-only when every path it adds, modifies, renames or deletes is under `tickets/`. For a pull request the comparison is against its base; for a push, against the previous head of the branch.
- On a ticket-only change, CI still runs `check_language.py`, `check_publication.py --worktree` and `--staged`, `python3 scripts/tickets.py check` and the ticket tests. Every other job, and the full unit suite and report demos, is skipped with a job-level condition, so each skipped job is reported as skipped. This applies to pull requests and to pushes, including pushes to `main`.
- The detection fails safe: if the changed paths cannot be determined (a new branch, a rewritten history, a manual run or any error), CI runs everything.
- `python scripts/check_pr_image.py`, run on a clean tree whose diff against `origin/main` is ticket-only, exits successfully without a Docker build and says why; on any other diff it behaves as today. `AGENTS.md` and `docs/development.md` state this exception, and only this one.
- Non-goals: changing what runs for code or other documentation changes, adding branch protection, changing action pins, and the planning or build rules outside the three changes above.

## Decisions needed

The Requirements follow the recommended option of each.

1. How a ticket reaches `done`. (a) The builder sets it in its last commit and a CI check enforces it. (b) `tickets.py` infers `done` from GitHub once the pull request merges. Recommendation: (a). Option (b) needs network access and a GitHub login, which breaks offline use and Codex or OpenCode sessions without `gh`.
2. What counts as ticket-only. (a) Only paths under `tickets/`. (b) Also Markdown under `docs/`. Recommendation: (a). Documents under `docs/` hold rules and expected values that agents build from, and some are checked by tests.
3. Pushes to `main`. (a) Ticket-only pushes to `main` also take the light path. (b) `main` always runs everything. Recommendation: (a). The code on `main` is unchanged by such a push, and the run of the last code change already covers it.
4. The image gate on ticket-only changes. (a) `check_pr_image.py` detects them and exits without building. (b) The rules exempt them and agents do not run the script. Recommendation: (a). Agents keep running one command before every pull request, and the script decides.
