# ENG-119: Define what the spec field of a ticket means

## Goal

The ticket format defines `spec:` as "a tracked document this ticket depends on", but most tickets now point it at revision 1 planning drafts that their own Context calls "background only". A builder cannot tell from the field whether the linked file is binding. Have the owner choose one meaning for `spec:` and write it down in every place that defines the field, so that later tickets and tools use it consistently.

## Context

- Current definition, worded slightly differently in three places:
  - [tickets/README.md](README.md), front-matter template: "optional link to a tracked document this ticket depends on";
  - [tickets/PORTABLE_PROMPT.md](PORTABLE_PROMPT.md), line 73: "optional link to a tracked document the ticket depends on";
  - [docs/spec-development.md](../docs/spec-development.md#the-ticket-is-the-spec) states the ticket is the spec and that a linked document setting expected values is part of it, but does not mention the field.
- What `spec:` points at on `main` at `18f72e1` (open and closed tickets):

  | Target | Tickets | Status | What the ticket says about it |
  |---|---|---|---|
  | `docs/specs/imp-007-r7/spec.md` | 6: IMP-007, 007E, 007F, 007G, 007M, 007N | open | the approved "IMP-007 spec r7" contract; normative |
  | `docs/ux-p*.md` (tracked UX specs) | 15 | 11 backlog, 3 done, 1 superseded | the done ones call it their spec for the shipped SQLite UI; ANL-103, ANL-106 and ANL-107 say its original criteria were written for the shipped application and the ticket replaces them; the rest say nothing |

- ENG-114 repointed the 17 `spec:` values at the published drafts (its Decision 4, option B) and added the "background only" Context lines. Each published draft's own note says "The ticket that cites it is the spec; this draft is background."
- `scripts/tickets.py` parses `spec:` but no command uses its value. [ENG-103](ENG-103.md) check 3 plans to report `spec:` values that do not resolve to a tracked file, which would flag the 20 historical values unless the definition says how to treat them.
- The 17 draft-pointing tickets include ANL-008, APP-011D, APP-011H, APP-011I, OPS-014 and OPS-015, which are `ready`. Changing their `spec:` is a front-matter edit, not a gated-section edit, so it does not invalidate an approved hash.
- `public-docs-agent-rules` is held by ENG-115 while it runs; this ticket waits for it.

## Requirements

- Scope: the owner's choice under Decision 1, recorded in this ticket's Log, and the matching wording in `tickets/README.md`, `tickets/PORTABLE_PROMPT.md` and, if the chosen meaning needs it, `docs/spec-development.md`. The three places say the same thing.
- The definition says, for each category in the Context table, whether such a value is allowed and what it means for a builder.
- No ticket's `spec:` value changes under this ticket. If the chosen meaning makes existing values wrong, file a follow-up ticket that lists them (it would need `ticket-bulk-edit`).
- No change to `scripts/tickets.py` unless Decision 2 chooses one.
- Non-goals: publishing or rewriting any draft, implementing ENG-103.

## Decisions needed

1. What `spec:` means. Option A (recommended): "the primary reference document for this ticket", binding where the ticket says so and background otherwise, with the ticket's Context stating which; this fits all four categories without editing any `spec:` value, though tickets whose Context is silent about their UX spec would need a Context line, and a builder still reads the Context line. Option B: "a tracked document whose content is part of this ticket's spec" (binding); background drafts then move out of `spec:` into Context only, so the 17 draft-pointing tickets need `spec:` cleared in a follow-up, and the 20 historical values become non-conforming history. Option C: keep the current wording and add one sentence that a ticket's Context may mark the linked document as background; the smallest change, but the field alone still does not say whether the file binds.
2. Whether the field should carry the distinction in a machine-readable form, for example a `spec_role: normative | background` field checked by `tickets.py check`. Option A (recommended): no, decide the wording only; revisit if ENG-103 needs it. Option B: yes, add the field, its validation and tests here, which changes the front-matter schema and raises this ticket's risk.
