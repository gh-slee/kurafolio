# IMP-101: Decide how a user recovers from an import booked by mistake

## Goal

Sooner or later a user confirms the wrong file: an export from the wrong account, a file edited by hand, or a test. The approved import contract has no reversal: a committed import stays, and a later correct file corrects only what it covers. The owner needs to know what a user can do today in each case, and decide whether V2 needs an explicit "withdraw this import" before other people are invited.

## Context

### Background

- This is the most likely support question in real use, and a tracker that cannot undo a mistake loses trust quickly.
- Facts are append-only by design, so any answer is a new record that supersedes the old one. Nothing is ever deleted or edited in place.

### Scope

- In scope: a short options paper with a worked example per case, the owner's decision, and follow-up tickets for whatever is chosen.
- Out of scope: implementing a withdrawal, changing the r7 contract, editing individual holdings by hand.

### Implementation notes

- Cases to work through on a synthetic instance: (1) a newer correct snapshot follows a wrong one; (2) the wrong file was the newest and no newer one exists; (3) a file with purchase records that never happened; (4) a file from an account that is not the user's.
- For each case, record what the pages show before and after the remedy that exists today, with the commands or clicks used.
- Options to compare: (a) document the remedies that exist and add nothing; (b) a "withdraw import" action that writes superseding records and recomputes, available for the most recent import of a source only; (c) the same for any past import; (d) an administrator-only reset of one user's data. Give cost, risk and what each means for the audit trail.
