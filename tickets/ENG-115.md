# ENG-115: Route each ticket tier to a model and add per-tool agent definitions

## Goal

The owner wants to start a session in Claude Code, Codex or OpenCode, say "plan <ID>" or "pick up <ID>", and have the right model do the work, for anyone who clones the repository. The owner decided on 2026-11-17 that a frontier model plans and reviews every ticket and that standard models write all the code. This ticket records that split as the workflow's rule, changes what `agent_tier` means to match, and adds the tool configuration that hands planning, building and review to the chosen models.

## Context

- Verified on 2026-11-17: Claude Code reads AGENTS.md when there is no CLAUDE.md; its project subagents accept `model` and `effort`. Codex reads custom agents from `.codex/agents/*.toml` with `model` and `model_reasoning_effort` (from documentation; not tried); project config loads only for trusted projects. OpenCode reads AGENTS.md and project agents from `.opencode/agents/`; its model IDs include a personal provider name.
- `.codex/` is gitignored and `scripts/check_publication.py` rejects `.claude/agents/`, `.codex/agents/` and `.opencode/agents/`.
- `docs/agent-development.md` currently allows subagents only when explicitly requested.
- A session whose builder agent fails to load silently builds on its own model; the design must make that visible.
- Merged rules (ENG-112) that assume the tier decides who builds, as of `973ec54`:
  - `docs/spec-development.md` lines 87-91: `next` marks only standard tickets `no build plan`; a frontier ticket may be planned and built in one session; an `any`-tier ticket needs no Build plan.
  - `docs/spec-development.md` lines 144-148: "a builder at the ticket's `agent_tier` takes the Developer role".
  - `tickets/README.md` lines 75-87: the tier table's "Typical agents" column, "Pass your own tier to `next`" and "It must not implement one."
  - `tickets/README.md` line 229 and the `next` row of the script reference (line 325).
  - `AGENTS.md` lines 72-75 (run `next` with your own tier) and lines 108-113 (skip tickets marked `no build plan`).
  - `scripts/tickets.py` `cmd_next` (around line 466) marks only `standard` tickets; `next --plan` lists only tickets above `any`.

## Requirements

- Roles and models, as the owner chose on 2026-11-17:
  - Planner: Claude Opus 5.5 at high effort, in Claude Code. It writes the Build plan of every ticket, of every tier.
  - Builders: Claude Sonnet 5.5 at medium effort (Claude Code), GPT-6.1 Sol at high effort (Codex) and DeepSeek Flash (OpenCode). Any of the three may build a ticket of any tier once its Build plan is on `main`.
  - Reviewer: Claude Opus 5.5 at high effort, in a fresh context, for independent QA and Architect review.
  - The planner model never builds. It plans, reviews and hands the build to a builder model.
- `agent_tier` no longer decides which model may build. It sets how much the Build plan must cover and how the result is reviewed:
  - `any`: a short Build plan; review as the ticket's `review` field says.
  - `standard`: a full Build plan as `tickets/README.md` describes it.
  - `frontier`: a full Build plan that also gives independent expected values, negative cases, rollback and the points where the builder must stop and ask; the reviewer model's independent review is required before the owner's review.
- Every ticket, of every tier, needs a Build plan merged to `main` before a build is claimed. The plan-merges-first rule of ENG-112 stays: a planning session opens a docs pull request and stops; once the owner merges it, a builder in any of the three tools picks the ticket up from `main`. The rule that a frontier ticket may be planned and built in one session is removed.
- AGENTS.md gains a table of roles, models and effort, and these rules:
  - A session that cannot reach the configured model for its role stops and says so. It never does a builder's work on the planner model, or a planner's work on a builder model.
  - In Claude Code, "pick up <ID>" on a ticket without a merged Build plan runs the planner, which opens the plan pull request and stops; on a ticket with one, it hands the build to the builder agent.
  - In Codex and OpenCode, a builder session given a ticket without a merged Build plan reports that it needs planning and does not build it.
- The merged rules listed in Context are rewritten to match, so that no tracked rule lets the planner model build or stops a builder model from building a ticket of a higher tier. Builders know which `next` command shows every ticket that is ready to build.
- `scripts/tickets.py`: `next` marks a ticket of any tier without a Build plan as `no build plan`, and `next --plan` lists tickets of every tier that need one. Marking is not enforcement: refusing a claim without a Build plan stays with ENG-116.
- Claude Code: project agents for planner, builder and reviewer, each with `model` and `effort` set, so routing does not depend on personal settings.
- Codex: a project builder agent with `model` and `model_reasoning_effort` set.
- OpenCode: no agent file is committed and no tracked file contains a model ID specific to one person's provider; the AGENTS.md table names DeepSeek Flash and each user configures it.
- Each agent states its model in its first output, and the builder records it in the ticket Log and the outcome line.
- The publication guard and `.gitignore` allow exactly the new agent files, with tests.
- Until this ticket's pull request merges, the current rules apply, including to building this ticket.
- Non-goals: changing anyone's global configuration; refusing claims without a Build plan (ENG-116).
