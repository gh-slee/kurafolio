# PLG-105: Map Bull Bitcoin sell orders to canonical SELL activities

## Goal

The owner's rule is that tracked Bitcoin is purchases minus sales reported by the same exchange file, and the positions calculation (ANL-008) already counts accepted SELL facts. But the Bull Bitcoin parser rejects any order that is not `Funding` or `Buy Bitcoin`, so one sell row makes the whole file fail and no real sale can reach the database. Teach the V2 import path to read Bull sell orders as canonical SELL activities, while the shipped importers keep behaving exactly as they do today.

## Context

- Owner rule, confirmed 2026-11-10 in [PRODUCT_CONTEXT.md](PRODUCT_CONTEXT.md) ("Sales in an exchange file"): tracked quantity is purchases minus sales reported by the same exchange file; funding rows and withdrawals to the user's own wallet change nothing; a one-line notice appears when sales were counted.
- Filed from [ANL-008](ANL-008.md) Decision 10, which the owner accepted on 2026-11-20: "file a parser follow-up that maps Bull sell orders to canonical SELL activities". ANL-008 counts an eligible SELL's negative non-FEE legs on crypto instruments as the sold quantity, per crypto account, and tests this with synthetic accepted SELL facts only.
- Why P1 and not P0: the MVP list in [ROADMAP.md](ROADMAP.md) does not include it. But today a single sell row rejects the whole Bull file, so a user who ever sold through Bull cannot finish flow step 6 ("Imports a Bull Bitcoin transactions file") at all. If the owner's own files contain sells, this is an MVP blocker and should be P0.
- Where sales are refused today (merged code):
  - `parse_bull` in `src/kurafolio/source_formats.py` raises "Unsupported Bull order type at row N: <type>" for any other order type, requires `PAYIN_CURRENCY` CAD, and requires a Bitcoin payout for every non-funding order. It is a shared byte grammar: the shipped SQLite importer (`src/kurafolio/crypto.py`) and the V2 adapter both call it. `tests/test_crypto.py` asserts that a `Sell Bitcoin` row raises "Unsupported Bull order type", and the message is a locale key in `src/kurafolio/locales/en-CA.json`.
  - `BullBitcoinOrders` in `src/kurafolio/source_builtin.py` (adapter `0.1.0`, export version `bullbitcoin-orders-utc-v1`) emits only `CryptoTransaction(type="purchase")` and `CashFlow` records; its `Lifecycle` assumes a CAD pay-in.
  - The shipped source pipeline, `_capabilities` in `src/kurafolio/source_ingestion.py`, raises `unsupported_effect` for any completed crypto transaction that is not a purchase.
  - The V2 evidence projection, `src/kurafolio/ingestion/discovery.py`, raises `import_evidence_unsupported` for any crypto transaction whose type is not `purchase` or that does not have two legs, and has no role for a positive cash leg.
- Contract rules that apply: r7 [contract-appendix.md](../docs/specs/imp-007-r7/contract-appendix.md) allows the generic BUY role projection only for the plain purchase shape; "transfer/fee/sale/swap shapes require explicit roles from the reviewed wrapper/core shape rules or an unsupported result", with no provider branch in commit or projection. The leg roles are `ACQUISITION`, `PAYMENT`, `TRANSFER`, `FEE` and `OTHER` (`src/kurafolio/domain/canonical_v1.py`). The 0004 SQL validator already maps source type `sale` to kind `SELL` (`src/kurafolio/persistence/ingestion_schema.py`), and r7 [reconciliation.md](../docs/specs/imp-007-r7/reconciliation.md) stores SELL facts without computing a pool.
- AGENTS.md: shared byte grammars must preserve legacy IDs, amounts, dates and messages; never infer wallet totals or opening assumptions in a parser; synthetic fixtures only.
- Resources: `v2-import-worker` because `discovery.py` holds the checks the worker applies to parser output (IMP-007F holds it while it builds the worker); `provider-adapter-contract` for the adapter.
- Tests to start from: `tests/test_source_builtin.py` (V2 adapter against `parse_bull`), `tests/test_crypto.py` (shipped importer), `tests/test_source_submission.py` and `tests/test_web_source_submission.py` (shipped source pipeline), `tests/test_domain_bridge_v1.py`, and the discovery tests under `tests/test_ingestion_*.py`.

## Requirements

- Scope: the V2 import path reads completed, pending and cancelled Bull sell orders of BTC (Bitcoin on-chain) and LBTC (Liquid) for CAD and turns each into one canonical activity of kind `SELL`, through the Bull adapter, the shared grammar where needed, and the V2 evidence projection. Includes synthetic fixtures, tests and a docs update.
- Non-goals: sells of other assets or networks, or for a currency other than CAD (still refused with a clear message); cost basis, realized gain or proceeds analysis; any change to the positions calculation (ANL-008 already counts SELL facts); withdrawals, transfers or wallet balances; the shipped SQLite application's behaviour.
- A sell order is the Bull order type the owner confirms under Decision 1, with the crypto amount paid in and CAD paid out to the CAD balance. Its canonical activity has kind `SELL`, the order's status (`completed`, `pending` or `cancelled`) mapped exactly as purchases are, one negative leg of the sold quantity on the crypto account and instrument, and one positive leg of the CAD proceeds on the CAD balance account, with the leg roles of Decision 2. Its `acquisition_cost` and `acquisition_cost_cad` are null. Quantities keep their source digits and at most eight decimal places; nothing is rounded.
- Identity: a sell order's source ID is its order key, derived from the provider, source account alias and order ID exactly as for other Bull orders. Corrections, duplicates and same-file conflicts follow the existing rules.
- Files without sells: every existing record ID, order key, amount, date, revision digest, `legacy_semantic_hash`, coverage entry and diagnostic is byte-identical to today's output, for the shipped importer, the shipped source pipeline and the V2 path.
- Shipped importers keep today's behaviour exactly: the SQLite importer still rejects a file containing a sell row with "Unsupported Bull order type at row N: <type>", and the shipped source pipeline still refuses it as it does today. How the V2 path is kept apart is Decision 3.
- No inference: a sale never creates or changes a wallet total, an opening balance, a cash balance or a funding flow. The adapter still declares membership `unknown` and order coverage `partial`, and still emits its wallet warnings.
- Unsupported shapes are refused with a fixed message, not skipped: a sell of an asset or network the grammar does not support, a non-CAD payout, a payout not to the CAD balance, a quantity with more than eight decimal places, or a completed sell with a non-positive amount.
- Generic code: the V2 evidence projection gains a sale shape rule that names no provider; the provider-specific reading stays in the Bull adapter.
- Fixtures are synthetic: invented order IDs and amounts in the Bull column layout, under `tests/`. `examples/data/bull-orders.csv` is not changed.
- `docs/source-adapters.md` (or the Bull section of the import docs) says that V2 imports read sell orders and the shipped importer does not.

## Decisions needed

1. **Which Bull order type is a sale, and its exact columns.** The repository's tests use `Sell Bitcoin` as a synthetic label, but no file in the repository shows Bull's real sell rows.
   - (a) The owner checks a real export and confirms the `ORDER_TYPE` label, the pay-in and payout methods for BTC and LBTC sells, and whether `ORDER_SUBTYPE` varies, without sharing any personal data; the fixtures then copy only the column layout.
   - (b) Build to `Sell Bitcoin` with pay-in `Bitcoin On-Chain` or `Liquid Network` and payout `CAD Balance`, and refuse anything else.
   - Recommendation: (a), falling back to (b) if the owner has no sell rows to check.
2. **Leg roles of a SELL.**
   - (a) The sold crypto leg `PAYMENT` (the asset given up, as CAD is in a purchase) and the CAD proceeds leg `OTHER`.
   - (b) Both legs `OTHER`.
   - Recommendation: (a). No proceeds leg is ever `ACQUISITION`, so no rule looking for acquisitions can mistake a sale for a purchase; ANL-008 needs only that the crypto leg is not `FEE`.
3. **How the shipped importers stay unchanged.**
   - (a) A new adapter version and export version for the V2 path (for example `0.2.0` and `bullbitcoin-orders-utc-v2`), registered only where the V2 import catalog selects it. `parse_bull` gains an explicit opt-in for sells whose default keeps today's behaviour, and the shipped importer and the shipped source pipeline keep using the old version.
   - (b) Change the existing adapter, and let the shipped source pipeline refuse sale records itself.
   - Recommendation: (a). (b) would change what shipped users see when a file has a sell row, and AGENTS.md keeps the shipped application unchanged.
