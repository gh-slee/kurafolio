# ENG-112: Make the ticket the spec and the workflow spec-driven

## Goal

`docs/spec-development.md` already describes spec-driven development: a spec with an exact revision and content hash, owner approval of that revision (Gate A), PM, Architect, Developer and QA roles, and owner review before merge (Gate B). The ticket board never implemented it. Tickets have no revision or hash, so nothing notices when approved text changes. Approvals name a date, not a text. A builder cannot tell whether the design work is done. Make the ticket file itself the spec, with gated requirement sections, a hash of what the owner approved, acceptance criteria with IDs that tests and reviews can cite, and a separate Build plan written before a standard-tier model builds it.

## Context

- Process document: [spec-development.md](../docs/spec-development.md). Board rules: [README.md](README.md). Script: [`scripts/tickets.py`](../scripts/tickets.py), tests in `tests/test_tickets.py`.
- On 2026-11-17 the open board had 75 tickets. 41 had no separate spec, so the ticket already was the spec in practice; about 30 cited files that exist only on the owner's machine (`docs/specs/`, `work/`, golden cases).
- The triage in PR #64 changed the acceptance criteria of six approved tickets. Under the rule this ticket implements, such changes need the owner's confirmation. Migrating existing tickets is ENG-113, not this ticket.
- Which model plans and which builds, and per-tool agent files, are ENG-115. This ticket defines roles by tier, not by model name.

## Requirements

- The ticket file is the spec of record for one unit of work. Shared contracts, ADRs and golden cases live in tracked documents that a ticket links; a ticket must not depend on an untracked file.
- Gated sections: `## Goal`, `## Requirements` and `## Acceptance criteria`. Everything else (Context, Build plan, Plan, Decisions needed, Handoff, Log and the front matter) can change without new approval.
- The spec hash is SHA-256 over the gated sections after normalisation: line endings, trailing whitespace, surrounding blank lines and checkbox ticks do not change it. Headings inside fenced code blocks are not section boundaries.
- Approval of a spec is recorded as `spec_approved: sha256:<hash>` next to `gate_approval`, and only when the owner approves that text. The file stores only the approved hash; the current hash is always computed.
- A ticket whose gated sections no longer match `spec_approved` is not claimable, and the script says why.
- Each acceptance criterion carries an ID `AC-<ticket>-NN`. A criterion that only a reviewer can judge is marked `[review]`. The script reports criteria that no test file mentions, as information only.
- A `## Build plan` holds the design a builder follows: files, interfaces, test cases with expected values, what not to touch, and when to stop and ask. A standard-tier ticket without one is still offered, with a warning, until the pilot (ENG-116) shows the gate can be enforced.
- Transition: tickets without `spec_approved` keep working exactly as today under their existing `gate_approval`. Nothing in this ticket edits, hashes or re-numbers another ticket.
- `tickets.py check` output and exit code do not change for the current board.
- Non-goals: model routing and agent files (ENG-115), migrating existing tickets (ENG-113), publishing local specs (ENG-114), CI enforcement, and changes to the claim protocol.

## Build plan

- `scripts/tickets.py`:
  - `spec_sections(body)`: fence-aware split on lines matching `^## `; returns name to text, first occurrence wins.
  - `spec_hash(body)`: canonical text is, for each gated name in order, `## <name>\n` + normalised body + `\n`. Normalise by converting CRLF to LF, stripping trailing whitespace per line, replacing `- [x]` or `- [X]` at the start of a line (after indentation) with `- [ ]`, and stripping leading and trailing blank lines. A missing section contributes an empty body. Return `sha256:<hex>`.
  - `acceptance_ids(body)`: IDs matching `AC-<ID>-\d{2}` in the Acceptance criteria section, with a `[review]` flag.
  - `validate()`: only add an error when `spec_approved` is non-empty and not `sha256:` plus 64 lowercase hex characters.
  - `availability()`: after the gate check, if `spec_approved` is set and differs from the computed hash, return `(False, 'spec changed since approval')`.
  - `cmd_next`: with `--plan`, list as described in AC-07. Without it, append `; no build plan` to the reason for a `standard` ticket without one.
  - `cmd_spec`: the report in AC-03. Exit 1 when the approved hash does not match, else 0. Test references are counted by searching text files under `tests/` and `frontend/tests/`.
- `tests/test_tickets.py`: a `SpecTest` class with the fixed vector, tick, Handoff, fenced-heading and changed-criterion cases, `next --plan`, the drift refusal in `next`, the `spec` command output and the malformed-value error.
- Documentation as in AC-01, AC-02 and AC-09. Keep `AGENTS.md` changes to a few lines.
- Do not touch: the claim, heartbeat, release and cleanup code paths; any other ticket file; the publication guard. Exception added after the Architect review: `takeover` also refuses a drifted spec unless `--force` (owner instruction) is given, so a stale claim cannot resume on unapproved text.
- Added after review: duplicate gated headings are a `check` error; fences close only on a matching marker; all checkbox styles and bare carriage returns are normalised; `spec --base REF` compares the gated sections with another ref and `spec` names the checkout it hashed.
- Stop and ask if: a requirement here would change how an existing approved ticket is treated.
