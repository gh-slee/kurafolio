# ANL-008: Project source-neutral positions and BTC Option A

## Goal

Add canonical authority selection and a coherent calculation snapshot service for securities and acquisition-only BTC, keeping old report read paths.

## Requirements

### Owner decisions recorded 2026-11-10

- Positions are grouped by asset class, not by institution. A Bitcoin ETF is a security. Coins held directly are crypto whether the record came from an exchange plugin or a broker plugin. Total counts each holding once.
- Tracked crypto quantity is purchases minus sales reported by the same exchange file. Funding rows and withdrawals to the user's own wallet change nothing. No opening balance, wallet check or income. Flag when sales were counted so the page can say so.
- A position missing from a newer broker snapshot is treated as sold when that file covers the position's account. An account absent from the whole file stays unchanged, and the import preview asks whether to keep it or mark it closed (owner confirmed 2026-11-10).
- Book cost and unrealized gain are exposed where the source provides cost (the Wealthsimple holdings file has `Book Value` columns). Unrealized gain is live market value minus book cost. A source without cost yields "unavailable", never zero. Crypto cost is the sum of purchase spending.
- Broker cash is a position class of its own and is part of Total as a separate "Cash" line.
- See [PRODUCT_CONTEXT.md](PRODUCT_CONTEXT.md).

- `value` and `values` disagree in exactly one case: a tracked crypto group whose quantity is exactly zero and that has no quote (Decision 12). Its `value`, `value_basis` and `value_as_of` are `None`, and `values[Y]` is `Decimal(0)` for every report currency Y. In every other case, a `None` `value` gives `None` in every `values[Y]`. `value_basis` keeps its closed set and is `None` in that case; no field or code is added for it.
- These field names line up with the ANL-012A read contract: calculation ID, generations, valuation time, `known_subtotal`, nullable `complete_total`, dates and typed codes. ANL-012A owns the HTTP DTOs.

### Reader rules (`read_accepted_state`)

1. Preconditions, checked first, in the caller's open transaction:
   - `current_setting('transaction_isolation')` is `repeatable read` and `current_setting('transaction_read_only')` is `on`; otherwise `projection_snapshot_required`.
   - `ledger.tenant_id` and `ledger.portfolio_id` equal `context`; otherwise `projection_scope_mismatch`.
   - `wl_pg.alembic_version` holds exactly one row whose value is in `SUPPORTED_REVISIONS`, a tuple constant in `projection/accepted.py`; otherwise `projection_schema_unsupported`. The constant starts as `("0004_ingestion",)`. It must list `0004_ingestion` and every later revision file under `src/kurafolio/persistence/migrations/versions/` at build time: APP-011I plans `0005_invite_status` and APP-011E plans `0006`. Add a later revision only after checking that it leaves the twelve `READ_TABLES`, `wl_pg.accounts`, `wl_pg.instruments` and the reader's grants unchanged; if it changes any of them, stop and ask. A default-suite test compares the constant with the revision files from `0004_ingestion` on, so a later migration pull request that forgets to add its revision fails there instead of making every positions read fail on an upgraded database.
   - `wl_pg.instance_state` row 1 is ready; otherwise `restore_required`.
   The reader never opens, commits or rolls back a transaction, and never sets a role or setting. Every query also filters on the context's tenant and portfolio, in addition to RLS.
2. Read `wl_ingestion.roots` for the generations. With no row, return an empty state with generations 0.
3. Plan index. Parse each `accepted_plans.canonical_bytes` once, ordered by `created_at, id`. For each fact whose `action` is not `duplicate`, map `accepted_revision_id` to `(plan, member_id)`; the first plan wins, as in `_BASIS_ACCEPTED_ROWS`. Index each plan's `mappings` by `(member_id, entity_kind, local_id)` to `(id, version)`.
4. Entities for a revision R: take `(plan, member)` from the index, then the plan's mapping for each local ID that R's typed bytes name (`source_account_local_id`, `asset_local_id`, a leg's `account_local_id` and `asset_local_id`). Then load `wl_pg.accounts` or `wl_pg.instruments` by `(id, version)` for role, category, label, kind, currency, ticker, MIC, symbol, network and settlement identity. Anything missing raises `projection_reference_missing`. This uses the mapping pinned when the fact was accepted (Decision 1).
5. Holdings, one `HoldingsHead` per `snapshot_heads` row with `fact_kind = 'holdings'`:
   - S is `source_revisions[latest_revision_id]` (collection `snapshots`).
   - Each local ID in S's `position_local_ids` resolves through `lineage` (`input_id` = S's `input_id`, collection `records`, that local ID) to a `source_revisions` row holding a typed Position.
   - Keep the positions whose resolved account is the head's `account_id` and whose instrument is inside the head's scope (`all`; `category` matches instrument kind; `instruments` lists the ID).
   - Coverage status: of S's `coverage_local_ids`, resolved the same way, the one Coverage of kind `holdings` whose account maps to the head's account. None or several raises `projection_head_inconsistent`; so does a position kept by two heads.
   - The complete-base revision is not read. Under the owner's rule, a position missing from the newest snapshot of a covered account is sold (Decision 8). An account counts as covered when the newer file has a holdings coverage entry for it, whatever its declared status, because that entry is what moved the account's head.
   - This deliberately departs from r7 [reconciliation.md](../docs/specs/imp-007-r7/reconciliation.md), which says omissions under a newer `partial` observation stay unresolved and that 008 consumes the uncertainty markers, and from golden case G02. The departure is the owner's decision (Decision 8 (a), accepted 2026-11-20). Reviewers should not report it as a contract violation; 0004 still stores the markers unchanged.
   - An account the newer file does not list keeps its own older head unchanged. ANL-008 reads no "closed" state: r7 has none. [IMP-007T](IMP-007T.md) adds the import preview's "keep, or mark closed?" question and stores the answer, and a later positions ticket reads it (Decision 9).
6. Activities, one `ActivityFact` per `activity_heads` row: R is `source_revisions[revision_id]`, typed Activity; `active` comes from the head. `mirror` is true when R, or an ancestor reached through `parent_id`, is the `left_revision_id` of an authority link whose latest revision (highest `revision` for its `id`) has `decision_kind = 'mirror'`. A mirror fact itself never gets a head, so it is never read as an acquisition. `has_crypto_fee` is true when a listed fee's asset maps to a CRYPTO instrument with a positive quantity; unknown fees (`null`) give false.
7. Decimal tokens become `Decimal(token)`; they were validated at admission. The result is sorted: heads by `key_digest`, positions by `revision_id`, activities by `economic_group_id`.

### Calculation rules (`calculate`)

- Arithmetic runs in `localcontext(Context(prec=120, rounding=ROUND_HALF_EVEN, traps=[InvalidOperation, DivisionByZero, Overflow]))`. Sums and products of admitted tokens (at most 38 significant digits) stay exact; only FX division rounds. Results are not rounded. Display rounding belongs to the page; tests use `ROUND_HALF_UP` to two places, as `formatting.py` does.
- Asset class of a holdings position, by instrument kind:
  - SECURITY is `securities`. A Bitcoin ETF, or any security with ticker `BTC`, stays here.
  - CASH is `cash`, valued at par: `Money(quantity, instrument.currency)`, basis `par`, cost `not_applicable`.
  - CRYPTO on an `investment` account is `crypto`, valued like a tracked crypto position. CRYPTO on a `crypto` account is a balance observation: it adds zero and counts under `excluded["balance_observation"]` (Decision 3).
  - UNSUPPORTED is `unsupported`, with gap `unsupported_position`.
  - Heads on `funding` accounts are skipped. Funding flows never become cash.
- Assumption `missing_from_newer_snapshot_is_sold` is listed whenever the state has at least one holdings head on a non-`funding` account whose `coverage_status` is not `complete`. The calculator does not read the complete base, so it cannot tell which positions were dropped; it names the rule whenever the rule may have applied without a complete declaration (Decision 8). It changes no value and adds no gap. With only `complete` heads, or no holdings heads, it is not listed.
- Security value:
  - With `unsupported_reasons` (for example `signed_position`), the position is kept with value `None` and gap `valuation_not_implemented`.
  - An accepted CORPORATE_ACTION activity with a leg on the instrument gives value `None` and gap `corporate_action_unresolved` (Decision 11g). This is the narrow guard only; the full check that a quote and a quantity share a corporate-action basis (golden case G19) is deferred to MKT-009B, which owns quotes.
  - With a quote for `Listing.of(mic, ticker)`: `quantity × quote.price`, basis `quote`, `value_as_of` the quote's `as_of`. A quote whose currency differs from the instrument's gives value `None` and gap `quote_currency_mismatch`, with no fallback.
  - With no quote: the snapshot's `market_value`, basis `source_reported`, `value_as_of` the snapshot time token, code `source_reported_value` (Decision 4).
  - Otherwise `None` with gap `value_unavailable`.
- Security cost and gain: `cost = cost_native`, and `book_cost_cad = cost_cad`, kept apart. `cost_native` of `None` gives cost status `unavailable` and gap `cost_unavailable`. Gain is `value − cost` only when both are known and share a currency; otherwise it is `None`. `gain_values` converts that native gain with the same FX as values (Decision 5).
- Crypto tracked positions come from activities, grouped by `(leg.account.id, leg.instrument.id)` for CRYPTO instruments:
  - Skip heads with `active=False` (`void`) and `mirror=True` (`mirror`).
  - BUY: `completed` with no unsupported reasons is eligible. `pending`, `cancelled` and unsupported count under those names. Its purchased quantity is the sum of positive ACQUISITION legs on CRYPTO instruments. A BUY with none (a security bought with BTC) counts as `non_crypto_purchase`. Payment legs never reduce tracked crypto.
  - SELL, when eligible: sold quantity is minus the sum of negative non-FEE legs on CRYPTO instruments, in the same group. An eligible SELL with no such leg raises gap `sale_shape_unsupported` and makes the crypto class and Total `complete_total` `None`.
  - TRANSFER, FUNDING, FEE and INCOME count as `not_acquisition` and add zero. CORPORATE_ACTION and UNSUPPORTED count as `unsupported`.
  - Per group, tracked = purchased − sold. Any sale sets `sales_counted`, assumption `sales_counted` and `sales_counted_count`. Tracked below zero gives quantity `None`, value `None` and gap `sales_exceed_purchases`; never clamp. Tracked zero is a known zero with quantity 0, valued as "Tracked zero" below says (Decision 12).
  - Cost is the sum of eligible BUYs' `acquisition_cost`. Any `None` gives cost `None`, status `unavailable` and gap `cost_unavailable`, never a partial sum. Mixed currencies give `cost_currency_mixed`. Gain is value converted to the cost currency minus cost. When `sales_counted` it is `None` with code `sales_counted` (Decision 6).
  - Any eligible activity with `has_crypto_fee` adds assumption `crypto_fees_not_deducted`.
  - Tracked zero (Decision 12). A group's tracked quantity is exactly zero only when its purchases are exactly offset by sales: purchased quantity sums positive legs and sold quantity sums negative legs, so a group with sales and no purchases goes below zero. A zero group therefore always has a counted sale.
    - With a quote: value `Money(0, quote.currency)`, basis `quote`, `value_as_of` the quote's `as_of`. Conversion follows the ordinary rule below, so a missing FX table or currency still gives `None` in that currency and `fx_unavailable`. The owner's decision covers only an absent quote.
    - Without a quote: quantity 0. `value`, `value_basis` and `value_as_of` are `None`, because there is no currency basis. `values[Y]` is `Decimal(0)` for every report currency Y, set directly with no conversion. The position gets no `quote_unavailable` and no `fx_unavailable`, even when `inputs.fx` is `None` or lacks a report currency.
    - Cost and gain, in both cases, follow the cost bullet above unchanged. Cost is the sum of the eligible BUYs' purchase spending, `known`, or `None` with `cost_unavailable` or `cost_currency_mixed` as usual. Gain is `None` with code `sales_counted` (Decision 6), and every `gain_values[Y]` is `None`. No gain conversion runs, so the gain adds no FX gap.
    - Everything else is unchanged: assumptions `acquisitions_assumed_held` and `sales_counted`, `sales_counted_count`, and for LBTC `btc_equivalent` true with code `valued_as_btc_equivalent`. The group adds 0 to `btc_equivalent_quantity`.
    - The rule covers activity groups only, because the owner's decision names tracked quantity. A CRYPTO holdings row on an `investment` account with quantity 0 and no quote follows the ordinary missing-quote rule: value `None` and `quote_unavailable`.
- Crypto value: BTC (network `bitcoin`) uses `crypto_quotes["BTC"]`. LBTC (network `liquid`) also uses the BTC quote, 1:1, with code `valued_as_btc_equivalent` (Decision 11b). Both set `btc_equivalent`. Other symbols use their own quote. A missing quote gives value `None` with gap `quote_unavailable`; the quantity stays. The one exception is a tracked group whose quantity is exactly zero, which "Tracked zero" above values (Decision 12). `btc_equivalent_quantity` sums the BTC and LBTC groups and is `None` if any is `None`. `basis` is always `acquisitions_assumed_held`, and that assumption is always listed when a crypto position exists.
- Conversion to each report currency Y: the same currency is unchanged. Otherwise `amount / per_pivot[X] × per_pivot[Y]`, with the pivot's own rate taken as 1. A missing FX table or currency gives `None` and one gap `fx_unavailable` per instrument. A tracked zero without a quote is not converted; its `values` are 0 (Decision 12).
- Aggregation, per class (`securities`, `cash`, `crypto`) and for Total (every position, including `unsupported`), per currency Y:
  - A position is known in Y when `values[Y]` is not `None`. A tracked zero without a quote is known 0 in every Y (Decision 12): it adds 0 to `known_subtotal[Y]` and never makes a `complete_total` `None` by itself.
  - `known_subtotal[Y]` is the sum of the known `values[Y]`. It is `None` when the scope has positions but none is known in Y. It is 0 for a class with no positions, and for a class whose known positions are all zero.
  - `complete_total[Y]` equals `known_subtotal[Y]` when every position in scope has a known `values[Y]` and no class-level gap applies; otherwise `None`.
  - `native_known` sums the known native `value`s per value currency. A tracked zero without a quote has no native value and adds nothing.
  - `unknown_value_count` counts the positions in scope whose native `value` is `None`, except tracked zeros without a quote.
  - Never add different currencies.
  - `complete_total` means "every tracked position is valued". It never claims whole wealth: built-in sources declare membership `unknown`.
- Nothing in the output names custody, a wallet or an opening balance, and no field claims a verified balance.
