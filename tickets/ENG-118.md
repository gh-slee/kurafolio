# ENG-118: Verify the SHA-256 that tickets record for linked spec documents

## Goal

Tickets link the documents that set their expected values together with a SHA-256 of the linked file, so a later edit to a golden case or contract file is visible as a change to the tickets that rely on it. Those hashes are written by hand and nothing checks them, so an edit to `docs/golden-cases.md` can land while every citing ticket still shows the old hash. Add a rule to the ticket script that recomputes each recorded hash from Git and reports any that do not match.

## Context

- Rule being enforced: "A linked document that sets expected values is part of the spec: link it at a commit, and treat a change to it as a change to the tickets that rely on it" ([spec-development.md](../docs/spec-development.md#the-ticket-is-the-spec)). [docs/golden-cases.md](../docs/golden-cases.md) and the published drafts under `docs/specs/v2-drafts/` repeat it in their introductions.
- Link forms in ticket Context, introduced by ENG-114:
  - `[docs/golden-cases.md](../docs/golden-cases.md) (sha256:<64 hex>)`, 32 occurrences at `18f72e1`;
  - `[docs/specs/imp-007-r7/](../docs/specs/imp-007-r7/README.md) (index sha256:<64 hex>; the index lists the SHA-256 of each file)`, 8 occurrences.
- [docs/specs/imp-007-r7/README.md](../docs/specs/imp-007-r7/README.md) has a Files table with one row per published file: a link relative to the README (including `fixtures/case-matrix.json`) and the SHA-256 in a code span in the last column. 20 rows.
- Baseline: at `18f72e1` all 40 ticket links and all 20 README rows match the SHA-256 of the file's Git blob at `HEAD`. A new rule must pass on that board.
- Text that looks similar but is not a document hash: `spec_approved: sha256:<hex>` in front matter (the gated-section hash), and the placeholders `sha256:<hash>` and `sha256:…` inside code spans in [ENG-112](ENG-112.md), [ENG-114](ENG-114.md), [PORTABLE_PROMPT.md](PORTABLE_PROMPT.md) and [spec-development.md](../docs/spec-development.md).
- Why Git blobs: the repository has no `.gitattributes`. On a clone with `core.autocrlf=true` (common on Windows) the worktree bytes of a Markdown file differ from the committed bytes, so hashing worktree files would report false mismatches. The blob content is the same on every clone.
- Script today: [scripts/tickets.py](../scripts/tickets.py) is standard library only. `validate(tickets)` checks front matter and sections without a repository root; `cmd_check` calls it and is run by `RepositoryTicketsTest.test_repository_tickets_are_valid` in [tests/test_tickets.py](../tests/test_tickets.py), which calls `validate()` directly. A `git(root, ...)` helper already exists. The same test file has a temporary-repository helper for Git-backed tests.
- Overlap: [ENG-103](ENG-103.md) (backlog, gated) plans a read-only `doctor` command whose check 3 reports `spec:` values and relative body links that do not resolve to a tracked file. Hash verification is a close neighbour: it needs the same link parsing and the same tracked-file lookup. [ENG-104](ENG-104.md) depends on ENG-103. Whether to fold this into ENG-103 is Decision 1.
- `public-docs-agent-rules` is held by ENG-115 while it runs; this ticket waits for it.

## Requirements

- Scope: a rule in `scripts/tickets.py` that verifies recorded document hashes, its tests in `tests/test_tickets.py`, and a short description in `tickets/README.md` of the link form and what the rule checks.
- What is checked:
  - In each ticket file (`tickets/<ID>.md`), every Markdown link to a relative path that is immediately followed by ` (sha256:<digest>` or ` (index sha256:<digest>`. The digest is compared with the linked file.
  - In `docs/specs/imp-007-r7/README.md`, every Files-table row with a relative link and a 64-hex SHA-256 in a code span; paths resolve relative to the README's directory.
- Grammar: a digest is exactly 64 lowercase hexadecimal characters. After a link, `(sha256:` or `(index sha256:` followed by anything else is a finding. Text inside code spans and fenced code blocks, and front matter, is ignored, so `spec_approved:` and the placeholders above are never checked.
- Paths: ticket links resolve relative to `tickets/`; an `#anchor` is dropped; a path that leaves the repository is a finding.
- Hashing: SHA-256 of the Git blob content read through `git cat-file` at the ref chosen under Decision 3, never the worktree file. A linked path that is not tracked at that ref is a finding.
- Report: one line per finding with the ticket ID (or README path), the linked path, the recorded digest and the computed digest or the reason.
- Where it runs and how it fails: as chosen under Decision 2. Whatever is chosen, `RepositoryTicketsTest` (or a sibling test) runs the rule on the real repository, and the current board passes.
- Without a Git repository: as chosen under Decision 4. Inside a repository the rule never skips silently.
- `scripts/tickets.py` stays standard library only; the only external command is `git`.
- Non-goals: generating or rewriting hashes, checking `spec:` values or links without a hash (ENG-103 check 3), checking hashes in other documents, calling GitHub.

## Acceptance criteria

- [ ] AC-ENG-118-01: On the board at the commit the change is built from, the rule reports no findings, and the test that runs it on the real repository passes.
- [ ] AC-ENG-118-02: In a temporary repository, a ticket link whose digest differs from the blob is reported with the ticket ID, the path and both digests.
- [ ] AC-ENG-118-03: The same check catches a mismatched row in an r7-style README table, with the path resolved relative to the README.
- [ ] AC-ENG-118-04: A file committed with LF endings and checked out with `core.autocrlf=true` (worktree bytes CRLF) passes when its recorded digest is the LF blob's SHA-256.

- [ ] AC-ENG-118-06: `spec_approved: sha256:...` in front matter and `sha256:<hash>` or `sha256:…` inside a code span produce no finding.

- [ ] AC-ENG-118-08: `scripts/tickets.py` imports only standard-library modules, and `tickets/README.md` documents the link form and the rule.

## Decisions needed

1. Separate ticket or part of ENG-103. Option A (recommended): keep this ticket separate and small, so it can ship before ENG-103 is groomed; ENG-103 later reuses its link parser. Option B: fold it into ENG-103 as a seventh `doctor` check and close this ticket as superseded; this delays it behind ENG-103's gate and its larger scope, and ENG-104 waits on the combined work.
2. Where the rule runs and whether a mismatch fails. Option A (recommended): inside `check` as an error, so the existing test suite and CI fail on a stale hash; editing a cited document then requires updating every citing ticket's hash in the same PR (11 tickets link `docs/golden-cases.md` at `18f72e1`), which makes the re-approval rule visible and needs `ticket-bulk-edit`. Option B: a warning printed by `check` that does not change its exit code. Option C: only in a separate command (`doctor` or `hashes`) that CI does not run.
3. Which Git content to hash. Option A (recommended): the index (`git cat-file blob :<path>`), which equals `HEAD` on a clean checkout and in CI, and also catches a staged edit to a cited document before it is committed. Option B: `HEAD:<path>`, which checks only what is committed.
4. Behaviour when the script runs outside a Git work tree (for example, from an exported source tree). Option A (recommended): skip the rule and print one line saying the hashes were not verified, without failing. Option B: fail `check`.
