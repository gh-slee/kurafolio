# OPS-101: Run an independent security review of V2 before other people are invited

## Goal

V2 holds several people's financial records behind one sign-in page. Each ticket had its own review, but nobody has looked at the assembled system the way an attacker would. Before the owner invites anyone else or makes the instance reachable from outside the machine, one session that built none of it reviews the running MVP and its code for the ways one user could reach another's data, or an outsider could get in.

## Context

### Background

- Tenant isolation is enforced in SQL functions and row-level rules across four migration revisions written by different agents. The seams between them are where mistakes hide.
- This is a review ticket. It finds and records; fixes go to new tickets.

### Scope

- In scope: the V2 API, sign-in and sessions, tenant isolation in every `/api/v2` route, the import upload path, the worker and launcher boundary, secrets handling in the compose stack, dependency advisories, a written report.
- Out of scope: the shipped SQLite application, load testing, fixing findings, a paid external penetration test.

### Implementation notes

- Work on a disposable synthetic instance from the OPS-021 compose file with two users. Never test against a real instance.
- Checklist to cover at least: every route with user A's session and user B's identifiers; every route without a session, with a wrong origin and without the CSRF token; session fixation, logout and password change; invitation and reset tokens (guessing, reuse, expiry); upload limits and malformed framing; error bodies and logs for leaked content; the database roles (can the API role read a table directly?); container settings against `compose.yaml`; secrets in images, logs and environment.
- Rate each finding as critical, high, medium or low, with the request or command that shows it.
- Critical and high findings block inviting other users. The report says so in its first line.
