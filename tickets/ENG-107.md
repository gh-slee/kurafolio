# ENG-107: Fix the timing race in the regular parser upload browser test

## Goal

One browser test fails now and then for reasons unrelated to the change under test. With several agents opening pull requests, each false failure costs a rerun and teaches agents to distrust CI. Make the test deterministic.

## Context

### Current behaviour

- On 2026-11-11 the same commit ran CI twice. `browser-workflow` passed in one run and failed in the other; the commit changed Markdown only.
- The failure: `frontend/tests/browser/workflow.spec.ts:676`, "regular parser upload reviews mappings and publishes without hand-written contexts". Line 728 expects an alert containing `request_failed` within 5 seconds and no alert appears.
- The test's own comment at line 729 says the worker may finish before the retry, so the step depends on which of two things happens first.

### What the failed run shows (added by planning, 2026-11-19)

- The failure is CI run 43116016390, attempt 1, job `browser-workflow`, "Show bounded synthetic browser failure context" step. Attempt 2 of the same run passed. The error context's page snapshot shows the Overview page of the new "Automatic parser synthetic portfolio" (heading "Start with your first observation"), not the Import & jobs page. No alert exists because the import form is no longer on the page.
- Likely cause, from the merged code at `a2f5f2b`: the test clicks "Create portfolio" (`workflow.spec.ts:688-690`) and then "Import & jobs" without waiting for the creation to finish. In `frontend/src/App.tsx`, `create()` awaits `POST /api/v1/portfolios` and then `switchPortfolio()`, which calls `clearTransport()` (aborts every in-flight request, `frontend/src/lib/api.ts:19-24`), awaits `client.cancelQueries()` and only then navigates to `/app/<new id>/overview`. When that POST is slower than the next test steps, the test fills in and submits the import form of the previously selected portfolio. The late `switchPortfolio()` then aborts the upload or preview request. `submit()` in `frontend/src/components/imports.tsx` deliberately ignores an `AbortError`, so no `request_failed` alert appears, and the page moves to the new portfolio's Overview.
- The interception at lines 713-724 is already deterministic: the first `source-import-previews` request always reaches the server and is then aborted. The retry step after line 729 waits for the mapping heading first, so it works whichever of the worker and the retry finishes first. The only other test in the file that creates a portfolio ("a dated BTC total can be submitted without either CSV", line 270) already waits for the new portfolio's Overview before it opens Import & jobs.

### Expected behaviour

- The test makes the failed request happen for certain (for example by intercepting that one request with the browser test tool) instead of relying on timing, then checks the alert and the retry.
- No change to what the test proves about the page.

### Scope

- In scope: this test, and any other step in the same file that depends on worker timing in the same way.
- Out of scope: retries for the whole suite, product code, the V2 suite (ENG-023).

- [ ] The test still fails if the alert is removed from the page.
- [ ] No global retry or longer global timeout is added to hide the race.

### Change 1: wait for the new portfolio before opening Import & jobs

Replace the "Create portfolio" click at lines 688-690 with this sequence:

```ts
const created = page.waitForResponse(
  (response) =>
    response.request().method() === "POST" &&
    new URL(response.url()).pathname === "/api/v1/portfolios",
);
await page
  .getByRole("button", { name: "Create portfolio", exact: true })
  .click();
const createdResponse = await created;
expect(createdResponse.status()).toBe(201);
const { id: portfolioId } = (await createdResponse.json()) as { id: string };
// ENG-107: switchPortfolio() aborts in-flight requests before it navigates,
// so wait for the navigation itself, not only for the POST response.
await expect(page).toHaveURL(new RegExp(`/app/${portfolioId}/overview$`));
await page.getByRole("link", { name: "Import & jobs", exact: true }).click();
await expect(page).toHaveURL(new RegExp(`/app/${portfolioId}/imports$`));
```

- Register `waitForResponse` before the click, so a fast response is not missed.
- Key the guard on the id from the response, not on the portfolio name: a repeated run creates many portfolios with the same name.
- `POST /api/v1/portfolios` returns 201 with a `PortfolioView` that has `id` (`src/kurafolio/web/api.py:311`). The front end calls it through `mutate("/portfolios", ...)`, which prefixes `/api/v1` (`frontend/src/lib/api.ts`).
- The existing "Import & jobs" click (line 691) is the one above; do not add a second one.

### Change 2: assert the alert only after the intercepted request has failed

Rewrite the route handler at lines 710-724 and the alert step at line 728 like this:

```ts
let interrupted = false;
let firstRequest = "";
let firstKey = "";
let firstStatus = 0;
let markAborted!: () => void;
const aborted = new Promise<void>((resolve) => (markAborted = resolve));
await page.route("**/source-import-previews", async (route) => {
  if (!interrupted) {
    interrupted = true;
    firstRequest = route.request().postData() ?? "";
    firstKey = route.request().headers()["idempotency-key"];
    try {
      const response = await route.fetch();
      firstStatus = response.status();
      await route.abort("failed");
    } finally {
      markAborted();
    }
  } else {
    await route.continue();
  }
});
await page
  .getByRole("button", { name: "Upload & preview", exact: true })
  .click();
// ENG-107: the first preview request reached the server and was then
// aborted, so the page must now report the failed request.
await aborted;
expect(firstStatus).toBe(202);
await expect(page.getByRole("alert")).toContainText("request_failed");
```

- Set `interrupted = true` at the start of the first call, not after `route.fetch()`, so only one request is ever treated as the first.
- Settle `aborted` in `finally` and assert the status outside the handler. An `expect` that throws inside a route handler leaves the request hanging until the 300-second test timeout and hides the reason.
- `await aborted` is bounded by the test's own `test.setTimeout(300000)`. Do not add a timeout to the alert assertion: once the abort is done, the remaining work is a React state update, well inside the default 5 seconds.
- Keep the locator `page.getByRole("alert")` exactly as it is. Do not filter it by text or scope it. A second, unexpected alert must still fail the test.
- Keep everything from the line 729 comment to the end of the test unchanged: the mapping-heading wait, the retry, the request-body and `idempotency-key` checks, `unroute`, the mapping review, both confirmations and the report checks.
