# PLG-102: Connect one institution through its read-only API

## Goal

Importing means exporting a file by hand each time. Some institutions offer a read-only API key that could fetch the same records on request. Build the first such connector end to end, so the user presses "Sync" instead of exporting and uploading, with the same preview and confirmation as a file import.

## Context

### Spec material

- Background only: the revision 1 planning draft [docs/specs/v2-drafts/WL-P1-001.md](../docs/specs/v2-drafts/WL-P1-001.md) (sha256:c58806576926113ec8c5d5d1f786bcb936d4f341de1b272b0bce876cad9c9564). Where it differs from this ticket, this ticket applies.

### Background

- Moved from P1 to P2 in the 2026-11-13 triage. The two institutions the owner uses are served by file plugins, and neither is known to offer a public read-only API. A connector means storing a user's API secret on the server, which is the largest new security surface on the backlog. That is worth building when a user holds an account at an institution with a suitable API.
- The candidate on record is Kraken read-only Spot history (open decision OD-07). It is a candidate, not a choice.

### Scope

- In scope: one provider, secret storage and rotation, a manual sync that produces a normal import preview, disconnect, tests against recorded synthetic responses.
- Out of scope: scheduled sync (a follow-up once manual sync is proven), any permission that can trade or withdraw, more than one provider, screen scraping or sharing a brokerage password.

### Implementation notes

- The key the user supplies must be read-only. The connector checks the key's permissions with the provider before saving it and refuses a key that can trade or withdraw.
- Secrets are encrypted at rest with a key that is not in the database, are never returned by any route, never logged, and are removed on disconnect. The design of that storage is reviewed before any code (see Decisions).
- A sync fetches pages into the same normalized form a file plugin produces and enters the normal pipeline: preview, decisions, confirmation. Nothing is booked without the user's confirmation.
- A failure in the middle of a multi-page fetch books nothing and does not advance the saved position. A retry books each record once.
- Records that also arrived by file must reconcile to one event, not two.

## Acceptance criteria

- [ ] Given a read-only key, then connect succeeds and the secret cannot be read back through any route, log or export.
- [ ] Given a key that can trade or withdraw, then connect is refused and nothing is stored.
- [ ] Given a sync, then the user sees the normal preview and nothing is booked until they confirm.
- [ ] Given a failure on the third of five pages, then nothing is booked and a retry books every record exactly once.
- [ ] Given the same purchases imported earlier from a file, then the sync adds no duplicate.
- [ ] Given disconnect, then the secret is gone and imported facts remain.
- [ ] Given a restore from backup, then stored secrets are unusable until re-entered, like other credentials.
- [ ] All tests run offline against recorded synthetic responses; a real disposable account is used only by the owner, once, to confirm coverage.

### Tests

- Offline connector tests with recorded synthetic pages.
- Opt-in PostgreSQL tests for secret storage and isolation.

## Decisions needed

1. Whether to build an API connector at all now, and for which institution (OD-07). Recommendation: wait until a user has an account at an institution with a documented read-only API; Kraken stays the candidate.
2. Where the encryption key for stored secrets lives. Recommendation: a file secret supplied by the operator, like the other V2 secrets; never in the database or the image.
