# OPS-021: Provide a one-command V2 MVP deployment for a self-hosted instance

## Goal

The owner wants to use V2 for real as soon as the MVP works and give feedback from daily use. Today nothing starts a complete V2 instance: there is a PostgreSQL-only compose file and a V2 server command with many required arguments. Provide one documented way to start database, V2 API with the bundle, and import worker on a new empty instance.

## Context

### Current behaviour

- `compose.pg-foundation.yaml` starts PostgreSQL only and says it is an optional development foundation.
- `compose.yaml` runs the SQLite application (`web` and `worker` services, port 8000).
- `python -m kurafolio.web_v2 serve` needs explicit secret files, origin, host, port and `--schema-profile` (`src/kurafolio/web_v2/__main__.py:13-22`); migrations are separate operator commands ([postgres-foundation.md](../docs/postgres-foundation.md), [web-v2-identity.md](../docs/web-v2-identity.md)).
- The import worker and the 0004 migration do not exist yet (IMP-007F, IMP-007D).

## Requirements

### Expected behaviour

- A separate compose file for V2 with PostgreSQL, the V2 API serving the bundle, and the import worker, bound to loopback, on its own volume and its own port so it never touches a SQLite instance.
- A documented first-run sequence: create secrets, run migrations, create the first administrator, start. Each step is one command.
- Stop, start and upgrade keep data. A backup and an empty-target restore procedure are documented and tested on synthetic data.
- The page gallery or README gains a short "Run the V2 MVP" section that states what the MVP does and does not do.

### Scope

- In scope: compose file, first-run script or documented commands, container hardening equal to `compose.yaml`, a synthetic smoke test, documentation.
- Out of scope: public image publication (OPS-104), the guide for moving from the SQLite application (OPS-014; data is imported again, not migrated), release acceptance across platforms (OPS-015).

### Implementation notes

- Copy the hardening of `compose.yaml`: read-only root, dropped capabilities, no-new-privileges, memory and PID limits, loopback port.
- Reuse `scripts/postgres.py` and `scripts/docker_context.py`; the image must stay source-only and reproducible.
- Secrets are files, never environment values or arguments (AGENTS.md, web-v2-identity.md).
- Use the claim's `isolation_id` and `port_base` for every test container and volume. Never start against, or share a volume with, an existing instance.

## Acceptance criteria

- [ ] AC-OPS-021-01: Given a clean machine with Docker, when the operator follows the documented steps, then a V2 instance answers on its loopback port and the setup page loads in a browser.
- [ ] AC-OPS-021-02: Given the instance is stopped and started, then accounts and imported data remain.
- [ ] AC-OPS-021-03: Given a backup taken with the documented command, then it restores into a second empty instance and sessions are revoked there.
- [ ] AC-OPS-021-04: The V2 compose project uses names, volumes and ports distinct from `compose.yaml`; starting one never affects the other.
- [ ] AC-OPS-021-05: A synthetic end-to-end smoke test (register, enable a source, import the example holdings file, read `GET /api/v2/analysis/securities`) passes in CI or as an opt-in Docker test. It calls the API; the same journey in a browser is ENG-023.
- [ ] AC-OPS-021-06: The documentation lists what the MVP leaves out.
- [ ] AC-OPS-021-07: The pull request description opens its Change Summary by telling the owner whether the V2 MVP is ready for real use. It gives the start command, the first-use steps (register, enable a source in the Parser Plugin Store, import a file, open the analysis pages) and the state of every MVP ticket in [ROADMAP.md](ROADMAP.md) from `python3 scripts/tickets.py list`. If any MVP ticket is not done, it says "not ready yet" and names what is missing.
