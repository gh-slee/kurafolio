### What to check

The approved acceptance list has 36 cases, A07-01 to A07-36, in `acceptance.md` of the r7 bundle, with literal expected values in `oracle.json` (a tracked copy of the vectors is `tests/fixtures/ingestion/oracle.json`). Work through all of them on a disposable synthetic instance started from the WL-P0-021 compose file, or from the WL-P0-007D to 007F commands if 021 is not merged. They fall into six groups:

| Group | Cases | What it proves |
|---|---|---|
| Booking | A07-01 to 14 | First import, replay, overlap, duplicates, snapshots, corrections, multi-account and precision book the expected facts once |
| Tampering and staleness | A07-15 to 18 | An altered or outdated preview, a disabled source or an ended session books nothing |
| Isolation | A07-19, 26, 27, 33 | Two users never see each other's data; no file bytes remain in the database, logs or backups; roles can do only what is granted |
| Races and faults | A07-20 to 25, 35 | Concurrent confirm and cancel give one result; a failure at any statement leaves no partial booking |
| Limits and containment | A07-28 to 31, 36 | Upload limits at, below and above each threshold; the parser container cannot reach the network, host files or the Docker socket |
| Compatibility and restore | A07-32, 34 | The shipped application's paths are unchanged; a backup restores into two separate empty instances with unaccepted work inactive |

Derive every expected value yourself from the fixture files. Do not call the implementation to compute what it should return. A case you could not run is recorded as NOT RUN with the reason, never as passed.

## Acceptance criteria

- [ ] All four epic acceptance criteria pass with independently derived expected values.
- [ ] A results table lists each of A07-01 to A07-36 as PASS, FAIL or NOT RUN, with the command or test that produced it. It is committed under `docs/` or linked from the pull request, with no private data.
- [ ] Restore into two empty targets keeps unaccepted authority inactive.
- [ ] Findings are recorded; repairs go back through the owning child ticket.
- [ ] Each FAIL has a bug ticket that names the case, the expected value and the observed value. A FAIL in booking, isolation, or races and faults blocks WL-P0-015; the pull request says so plainly.
- [ ] The cases are automated where they can be, as opt-in PostgreSQL or Docker tests, so they run again in CI and for WL-P0-015.
