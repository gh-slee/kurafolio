# OPS-102: Document and test reaching the instance from a phone or another computer

## Goal

The MVP listens only on the machine it runs on. The owner and anyone they invite will want to open it from a phone or laptop. The server already refuses to listen on a network address without real TLS, which is right, but nothing tells an operator how to set that up safely. Provide one supported, tested way to reach the instance over HTTPS from other devices on the home network, and say clearly what is not supported.

## Context

### Background

- Without this, the first thing an operator does is weaken the bind address, or put the plain port on the network.
- Exposure to the public internet is a different risk level and is not part of this ticket.

### Scope

- In scope: an optional compose profile with a TLS-terminating reverse proxy, the exact origin and cookie settings, a guide for certificates on a home network, a test that signs in through the proxy, a "what not to do" section.
- Out of scope: public internet exposure, dynamic DNS, a VPN product recommendation beyond naming the option, single sign-on, changes to the server's own TLS rules.

### Implementation notes

- The server trusts no forwarded headers and needs the exact public HTTPS origin; behind a proxy, users can share a peer address, which affects the per-peer rate limits. Read the existing rules before choosing settings, and document the effect.
- Offer two documented routes and test the first: (1) the proxy profile with a certificate the operator supplies or generates for a private host name; (2) the server's own `--tls-cert-file` and `--tls-key-file`.
- Mention a private overlay network as a third option in one paragraph, without endorsing a product.
- The proxy container gets the same hardening as the others: read-only root, dropped capabilities, no new privileges.
- Session cookies must stay `Secure` with the `__Host-` prefix; the test asserts it.

### Where to start

- [web-operations.md](../docs/web-operations.md) (lines on HTTPS and reverse proxies), [web-v2-identity.md](../docs/web-v2-identity.md) (bind and TLS rules).
- The V2 compose file from OPS-021; `src/kurafolio/web_v2/__main__.py`, `config.py`.

## Acceptance criteria

- [ ] Given the documented proxy profile and a test certificate, then a browser on another host name signs in over HTTPS and completes an import on synthetic data.
- [ ] Given a request over plain HTTP to the proxy, then it is redirected or refused; the application port is not reachable from outside the compose network.
- [ ] Given a request with a forged forwarded header, then it gains nothing.
- [ ] The session cookie is `Secure`, `HttpOnly` and uses the `__Host-` prefix through the proxy.
- [ ] The guide states the effect on rate limits when users share the proxy's address.
- [ ] The guide has a short "not supported" list: plain HTTP on the network, public exposure without the owner's own review, wildcard origins.
- [ ] The default compose stack is unchanged and still binds to loopback only.

### Tests

- An opt-in Docker test that drives sign-in through the proxy with a disposable certificate.
