# PLG-101: Give contributors a guide and a test harness for new source plugins

## Goal

Only official plugins run in Kurafolio: written by the owner or a contributor, reviewed and merged in the repository (owner decision 2026-11-10). Supporting a new broker or exchange therefore depends on how easy it is for a contributor to write a plugin and prove it correct in a pull request. Provide a step-by-step guide, a synthetic-fixture test harness that runs in CI, and a review checklist, and link them from the Parser Plugin Store.

## Context

### Spec material

- Background only: the revision 1 planning draft [docs/specs/v2-drafts/WL-P1-003.md](../docs/specs/v2-drafts/WL-P1-003.md) (sha256:da998a0ababe4d9c5114997d505664bab7c038b46218b851913ae6e7b6af77a0). Where it differs from this ticket, this ticket applies.

### Background

- Every additional institution (PLG-103) is one use of this workflow. Without it each new plugin is a custom job for a frontier agent.
- The owner dropped "test your own plugin in the app". A contributor tests locally with the harness and in a disposable developer instance, never by uploading code in the browser.

### Scope

- In scope: the contributor guide, a harness command that runs a plugin against its fixtures and the shared contract checks, a template plugin, the review checklist in the pull request template or CONTRIBUTING, the link from the Parser Plugin Store page.
- Out of scope: any way to install, upload or enable an unreviewed plugin in a running instance; a plugin marketplace; API connectors (PLG-102); new institutions themselves (PLG-103).

### Implementation notes

- Build on what exists: [parser-sdk.md](../docs/parser-sdk.md), `examples/parser-plugin`, `src/kurafolio/source_testing.py` and the built-in plugins in `src/kurafolio/source_builtin.py`.
- The harness checks what a reviewer would otherwise check by hand: stable record IDs across a re-import, decimal strings and precision, dates with their precision, no network or file access, declared asset classes (APP-011H), help text in the three locales, and that a second import of the same file changes nothing.
- Fixtures are synthetic and legally clean: invented accounts and amounts in the institution's column layout. The guide says how to make one from a real export without copying personal data.
- The guide ends with the pipeline run: the plugin's fixture goes through import, preview, confirmation and the analysis pages on a disposable V2 instance.

### Where to start

- [parser-sdk.md](../docs/parser-sdk.md), [source-adapters.md](../docs/source-adapters.md), [web-v2-sources.md](../docs/web-v2-sources.md).

- The Parser Plugin Store page, `frontend/src/v2/sources.tsx`.

## Acceptance criteria

- [ ] Given the guide and the template, a contributor adds a synthetic third plugin with one command to scaffold it and one to test it, without editing core code outside the registry entry.
- [ ] Given that synthetic plugin, then its fixture completes import, preview, confirmation and appears on the analysis pages of a disposable instance, with no branch on the plugin's name in core code.
- [ ] Given a plugin that reads the network, writes a file, returns a float or changes IDs between runs, then the harness fails and names the rule.
- [ ] CI runs the harness for every plugin in the repository.
- [ ] The review checklist covers fixtures, precision, IDs, locales, licensing of the format documentation and what the plugin cannot know (for example cost or cash).
- [ ] The Parser Plugin Store links to the guide and says that plugins are added through reviewed pull requests.
- [ ] No route, command or setting lets a running instance load a plugin that is not in the installed package.

### Tests

- The harness tests itself with one good and several deliberately bad synthetic plugins.
