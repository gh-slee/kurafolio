## Grants, RLS and trust

There are three separate application login roles in the new profile: identity/source gateway, financial reader, ingestion worker. All have no role membership, ownership, superuser, BYPASSRLS, CREATE/CREATEROLE/CREATEDB, schema CREATE or unrestricted TEMP privilege. Operator/schema owner is not used by any app component. Function EXECUTE is revoked from PUBLIC, all app roles and inherited grants first; grant only the exact user/worker lists in sql-inventory.json. Helpers/trigger functions have no app EXECUTE. Gateway has no direct table/column SELECT/DML in private schemas; worker also has none. Launcher has no DB credential at all.

Ordinary financial role has SELECT only on all existing foundation/source read tables and new accepted_inputs/accepted_plans/source_revisions/activity_heads/snapshot_heads/mappings/authority_links/lineage/receipts/audit/outbox/roots. It cannot see transient stages/decisions/previews/members/leases/quotas or instance worker/control tables directly. SELECT is within trusted RequestDatabase's authenticated context and forced RLS, not a claim that stolen DB credentials are a per-user capability. No INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER/DDL or user/worker mutation function is granted to financial role in ingestion profile. Existing foundation/identity/sources profiles preserve their exact old grants; do not weaken their inventory checks to accept everything.

Every tenant table has ENABLE+FORCE RLS. Policies are exactly runtime_scope (TO financial role, USING tenant_id=current authenticated ledger.tenant_id AND portfolio_id=ledger.portfolio_id, no writes) and operator_scope (TO schema owner, USING/WITH CHECK true). Functions explicitly derive/filter scope from live auth or lease; definer ownership/RLS is not itself an authorization proof. Instance tables have no app raw grants/policies. Inventory checks table/column/function grants, effective PUBLIC/inherited privileges, role flags/memberships, owner, body/search_path, RLS/policy text, indexes/constraints/triggers and declared schema cardinality. No silent repair.

## Function payloads and responsibilities

User functions all use the six source-gateway principal/catalog argument types. _guard_user_v1 validates instance/schema initialized marker, exact actual DB realm, session/credential, source catalog digest, and sets scoped context. History and receipt replay use live auth first but skip mutable source/preview checks after proving an existing effect. New work also locks/rechecks exact source lifecycle and wrapper catalog. API-only fields are never forwarded as SQL authority.

- create_set_v1: operation_id, members[{connection_id,installation_id,format_version,declared_bytes|null}]. Reserve worst-case set capacity, exactly once.
- read_sets_v1/read_set_v1/read_preview_v1/read_receipt_v1: exact signed cursor/filter/limit or one opaque ID. No arbitrary table/filter/projection expression.
- decide_set_v1: set_id plus complete closed Decisions object. Append revision and enqueue prepare; reply202/RECONCILING until a proven immutable preview exists. No accepted entities written.
- reserve_member_v1: action reserve or bind. reserve includes set/member/expected_revision; bind additionally exact fence, raw digest/length and fresh handoff token digest generated by API. Binding is one-shot, selection unchanged. Return token expiry/opaque handoff metadata only to trusted API, never in public DTO.
- accept_preview_v1: operation_id,preview_id,preview_digest only. Load immutable plan and validate actual stage/decisions/live generations/references before _effects_v1. Exact existing receipt is recovered before mutable stale/expiry checks.
- cancel_set_v1: operation_id,set_id,expected_set_revision. Serialize against ACCEPT; winning cancellation fences all leases and starts cleanup. A committed set returns its original acceptance receipt.

Worker functions have (worker_uuid,token,closed_request,bytea|null). claim_member_v1 consumes the offered one-use handoff and returns scoped normalization lease; renew_member_v1 updates only current exact fence within deadline; admit_stage_v1 strictly validates minimal bytea/digests and job/source/session before insert; finish_member_v1 returns only fixed state/error/cleanup outcome. claim_plan_v1 claims prepare work rooted in the current authenticated CREATE/upload or explicit decision revision, or terminal cleanup work; read_plan_basis_v1 returns only scoped read basis under that lease and pinned accepted/mapping/control generations (paginated1..50, stale generation aborts). prepare_preview_v1 validates closed ReviewBundle bytea and its optional complete Plan against those exact stages/decisions/current refs and stores immutable preview, never finance. cleanup_set_v1 proves terminal fence/owned cleanup and purges only transient data; no accepted evidence DELETE.

_canonical_v1 recursively serializes controlled JSON exactly as the core canonical encoding; _validate_minimal_v1 and _validate_plan_v1 enforce every schema and semantic/reference predicate, not only digest equality. Bytea must equal its checked canonical encoding; duplicates/noncanonical numeric scale/extra keys cannot be lost through jsonb and accepted. Public JSON is strictly decoded before SQL; direct SQL payload jsonb still gets exact key/type/counter/scope validation. _quota_v1 performs shared locked admission/release, _references_v1 enforces scoped parent/entity/head/authority consistency, _replay_v1 reads only the operation namespace, _effects_v1 is the sole accepted mutation and _purge_v1 is transient-only. No app can EXECUTE them independently.

## Lock order and effects

Match existing source guard order: instance_state shared, instance_auth_state update, users then sessions, source catalog shared, portfolio key-share, source lifecycle root, enablements sorted by plugin/capability, foundation connections sorted id/version, connection_lifecycle sorted id. Then ingestion instance quota rows sorted bucket (only operations needing them), roots, sets, leases/previews sorted IDs, entity/mapping/source/economic/head rows by canonical key. No new path may acquire an earlier row after a later row. Cleanup worker follows the same live guard/realm derivation or maintenance fail-closed path. Rate consumption may be a separate short authenticated transaction, not a reason to reorder the financial transaction.

Under final locks recheck DB clock/session/source/generations after waits. Root counters are not old foundation candidate/job generation. ACCEPT inserts entities/mappings, necessary accepted input+plan bytes, new revisions/links/lineage, head CAS, receipt/audit, accepted_generation once iff a new authoritative source_revisions row or accepted head is added/changed; retained input/plan/duplicate lineage alone does not increment it, mapping_generation once iff accepted mapping/authority changes, and one outbox event iff any accepted/mapping change requires invalidation. Mapping-only accepted change uses event facts.accepted.v1 with unchanged accepted_generation and changed mapping_generation, empty changed-fact set; it is not investment growth. Duplicate-only with no mapping change has receipt/audit1 but no generation/outbox; exact replay creates no rows.

## Final guard clarifications

members explicitly stores all source enablement/availability/connection generations and wrapper digest captured at creation. Recheck them at reserve/bind, worker claim/admission/preparation and final ACCEPT; child context bytes alone do not store full DB authority. Set actor_user_id equals tenant_id under current one-user/one-portfolio identity and has the actual user FK. First create initializes a missing scoped ingestion root at zero; existing registration/portfolio creation semantics do not silently change.

During raw reception a normalize lease is offered with null token_digest and a deadline<=30s; a worker cannot claim it. bind sets the one-use token digest after exact raw reception, with offer expiry=min(bind clock+60s,raw_deadline). Worker ID is the configured trusted registry identity; raw_deadline was fixed at initial reserve clock+120s. Active claims require a bound token and matching source/session/realm. claim_plan_v1 accepts a fresh worker-generated256-bit token, selects exactly one eligible prepare/cleanup job under locks and stores its digest; prepare cannot use another job's lease.

Cleanup is a distinct work kind: current initialized realm, enabled registered worker and exact terminal lease/fence remain required, but an expired originating user session or disabled source must not prevent safe transient deletion. Cleanup cannot read plan basis/financial payload or mutate accepted tables, and returns content-free cleanup status only. Normalization/preparation/ACCEPT still require the original live user authority or a new user-originated decision. Never use cleanup privilege to bypass financial authorization.

Source original/correction/void remains in source_change and typed evidence. A separate explicit accepted parent overlay records accepted_change without falsifying source metadata. _validate_plan_v1 hashes the material financial projection fixed in fixture-appendix.md, comparing exact source key bytes as well as indexed hashes. It must not hash raw/local IDs or use a digest as evidence of economic equivalence.

Root control_generation increments once on a new successful decisions revision or winning user cancellation; set revision also advances. Create, upload, stage and successful prepare do not change it; prepare READY advances only set revision. Expiry/cleanup fences the affected set/leases and does not manufacture a financial generation. ACCEPT advances set revision once and accepted/mapping generations according to its actual effects. A receipt replay advances nothing. These are independent counters, never inferred investment returns.

Image contexts require scripts/docker_context.py and its dedicated regression tests in the finite proposed scope: copy only the two reviewed new Dockerfiles plus already-audited source/locks, never the whole checkout/private work. The source-only main candidate gate remains mandatory. Synthetic child/launcher build evidence must pin the exact base image, source manifest and actual immutable result; fixture placeholder image hashes are not that evidence. All full planning vectors may be embedded into the one reviewed public tests/fixtures/ingestion/oracle.json; the private planning directory itself is never published.
